# 待讨论的设计想法与需求

本文记录用户提出的两项设计需求及后续讨论，状态均为待设计、未实施，不归类为bug。用户明确要求暂时不做；本轮仅记录，不修改代码、运行配置或用户数据，不启动隔离环境。这里只记录目标、用户明确的边界和候选方案，不作为现行模型/API契约或实施授权。

## RULE-IDEA-001｜对话沉淀的项目规则透明管理

用户希望对话中逐渐确定的规则（例如如何启动程序）脱离个人设置，随着项目变化维护。用户理解这些规则可以写进助手，但当前助手不透明，难以查看和管理。

设计目标：用户能够查看、修改和管理沉淀的规则，知道当前生效内容及变化。待确认：规则最终归属于助手还是项目、与现有项目AGENTS.md的关系、固化与修订是否需要确认、来源与版本如何展示。讨论中的“助手维护、项目保存、独立入口管理”仅为候选方案，尚未定案。验收条件随模型/API设计补齐。

## PROC-IDEA-001｜原生bash启动进程的可见性与生命周期

用户担心助手通过bash启动服务后持续运行，无法知道服务是否退出，形成无人管理的遗留进程。用户指出Runtime挂载的是原生bash，无法可靠区分普通命令与启动服务的命令。

设计目标：明确助手执行所产生进程的归属、运行状态和结束边界，使用户能理解并管理持续运行的服务。用户已明确客户端断开意味着不再需要所属会话，应关闭会话；断线检测方式、关闭时的运行中止、进程清理，以及同一会话存在多个客户端时的判定仍需设计。关闭会话不应据此推导为删除历史，也不应直接等同于停止独立的测试环境。

待核实：Pi原生bash现有的超时、取消、子进程清理和后台进程行为，以及本轮结束、会话关闭和应用退出各自的执行边界。不能把命令字符串分类或助手自行声明用途当作可靠的进程管理保证；关闭Pi Session或取消工具调用不直接证明所有派生进程都已退出。验收条件随模型/API设计补齐。

## 后续讨论｜共享项目、多客户端与权限隔离

### 初始目标与关键约束

用户最初希望一份共享项目目录可以同时被多个客户端使用，因此要求server维护所有共享状态。客户端的连接与操作不能形成彼此独立的项目事实；需求、规则、会话、执行状态和权限需由server统一协调，具体持久模型与API尚未设计。

共享目录的致命约束有两点：原生Session本身没有文件锁能力；Session挂载的原生bash可以按宿主账号权限修改任意可访问的目录和文件。pwd/cwd仅为命令工作目录，不是安全边界。仅按项目加应用锁、过滤命令或依赖提示词，均无法阻止bash越过项目范围；两个不同项目的执行也可能修改相同文件。执行权协调与系统权限隔离是不同问题，不能互相替代。

用户考虑过Git工作副本、按客户端独占分配目录和容器隔离，但担心资源占用、初始化速度，以及多份代码同时存在时展示哪一份的问题。worktree可以分离工作副本，但不能单独限制bash越界；项目依赖、构建缓存及服务准备成本也需计入，不能只比较工作副本创建时间。

### 用户提出的管理员／访客协作方向

候选方向为一个具备读写能力的管理员与多个只读访客，共享开发代码知识来源。访客可通过单独的Office工具写需求文档，管理员根据需求修改代码。访客不需要关注需求执行进度，主要关心成品；不要求向访客展示开发日志、工具执行或任务队列。

两个环境必须区分：访客实际访问的是测试环境，绝不使用开发环境；但访客助手的回答基于开发环境代码和文档生成，只是不具备代码修改能力。不能把“访客不使用开发环境成品”误解为“访客助手不读取开发代码”，也不能擅自收窄为仅需求收集入口。

用户指出中间存在严重交互割裂，尚未形成完整解决方案。讨论中识别的一个风险是测试环境与开发代码版本错位：访客看到的成品可能不包含助手读到的新实现。候选处理是记录测试环境对应版本和助手读取依据，回答时区分已提供能力与开发中能力；共享开发目录持续变化也可能让一次分析读到不一致的文件状态。版本关联、需求交接、澄清和结果反馈如何贯通仍待设计，不能视为已经解决。

候选约束还包括管理员执行串行化、需求文档写入范围及版本冲突校验，以及按已提交需求版本执行。这些是讨论建议，尚未批准；管理员打开多个客户端时也不能仅凭“管理员只有一个”就推定没有并发写入。

### bash文件访问边界的候选方案

用户询问能否彻底限制bash超出pwd访问文件。讨论结论为需要操作系统执行层约束，而非cwd、提示词或命令字符串判断；可以保留Pi原生bash接口，把Pi Runtime及其派生进程放入受限执行环境，但具体可行性未验证。

| 候选方案 | 预期用途 | 限制与待核实项 |
| --- | --- | --- |
| Linux Landlock | 在启动Runtime工作进程时限制文件系统读写范围，由子进程继承，不复制项目目录 | 目标主机内核及ABI支持、Pi进程启动集成、依赖和专用可写目录、限制覆盖范围；不能假定当前环境已支持 |
| 容器或挂载命名空间 | 仅暴露允许访问的目录，分别只读或可写，并结合进程／网络约束 | 部署平台、挂载和权限配置、进程清理、资源成本及启动速度；不预先承诺绝对隔离 |
| 常驻受限环境 | 初始化后复用共享目录、依赖和缓存，减少按客户端或每轮创建环境的成本 | 管理员／访客权限必须仍有独立执行边界，不能在同一无隔离进程内仅靠角色切换；需要评估进程归属与回收 |

权限配置的候选方向：管理员可写允许的开发目录，访客Runtime只读开发代码；各自仅写专用临时目录及会话存储。运行工具所需的可执行文件和库可在项目外只读访问，因此“项目外禁止写入”与“项目外完全不可访问”必须区分。需求文档若只允许Office工具修改，可由单独的受控服务按对象定位写入；若直接给访客Runtime该目录写权限，bash也会获得同等能力，不能声称只能通过Office修改。

系统限制应在任何工具执行前建立，覆盖派生进程，并避免暴露宿主控制接口（如Docker socket）、外部可写句柄或绕过隔离的服务。文件权限与网络权限需分别考虑；容器配置、内核能力及宿主程序仍构成可信基础，不承诺在任何情况下绝对安全。受限环境可集中部署，不必为每位访客复制项目，但共享只读挂载不等于代码版本快照。

### Office／纯文本的独立生成工具

用户进一步明确：访客需要独立的文档输出工具，覆盖Office和纯文本文件。访客通常围绕系统询问，助手基于开发代码和文档解答；Bug或新需求可能在询问中逐渐发现，但不是对话的前提。访客也会直接要求生成说明文档、操作文档，或把已经讨论的内容整理成文件，供下载和分享；文档输出不限于Bug记录或需求交接，不要求每次询问都生成文件。这是已明确的需求方向，具体模型、API和工具方案仍待设计，不代表已经授权实现或改变现有Pi原生工具策略。

候选职责边界：助手组织内容，通过专用工具提交格式、文件名和内容；服务端校验调用身份、会话归属及输出许可，确定保存位置并生成文件。工具不接受任意宿主输出路径，访客Runtime不因此获得开发目录或需求文档目录的直接写权限。纯文本也通过相同的受控输出边界生成，不能仅因格式简单而改用具有目录写权限的bash/write。

Office的具体支持范围（Word、Excel、PPT）、内容输入结构、模板与排版能力仍待设计；纯文本的格式、编码和大小限制也需明确。候选返回包含产物标识、文件名、格式和大小，并通过核验归属的API预览或下载；文件归属、存储位置、保留期限、失败清理和重复调用处理需在正式模型/API中定义。生成产物与提交需求是两个独立意图，是否作为需求交给管理员及如何关联版本，不能由文件生成自动推定。
